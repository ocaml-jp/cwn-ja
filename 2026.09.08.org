* forcamla 0.4.0 - シンプルな Functional Reactive Programming
:PROPERTIES:
:CUSTOM_ID: 2
:END:
Archive: https://discuss.ocaml.org/t/ann-forcamla-0-4-0-simple-functional-reactive-programming/18501/1

** Christopher Sumnicht が発表しました


みなさん、こんにちは。

少し前に [[https://github.com/rxdt-labs/forcamla][forcamla]]（[[https://opam.ocaml.org/packages/forcamla/][opam]]）というパッケージを作りました（昨日まで discuss.ocaml.org の存在を知りませんでした）。非常に強力なスプレッドシートエディタのようなものだと考えていただければわかりやすいと思います。特に forcamla では、変数を「代入」するのではなく「等値化」します。また、forcamla はスプレッドシートの機能とイベントリスナーを組み合わせて、プログラムの実行を整理します。

*** 小さな例

#+begin_src ocaml
open Formula (* To use formula *)

let x = v 2 (* Create an integer term called x *)
let y = v 2 (* Create an integer term called y *)
let z = x + y
let () = x =: 3 (* Set x to 3, and z now is 5 *)
#+end_src

~z~ を再代入する必要がないことに注目してください。~z~ は ~x + y~ に「等値化」されており、~x~ や ~y~ が変化するたびに常に更新されます。

*** イベントリスナー

このフレームワークを使ってイベントリスナーを構築することもできます。以下にゲームの小さな例を示します。

#+begin_src ocaml
open Formula

type hero =
{
  (* A bunuch of fields *)
  health: int formula
}

let player =
{
  (* Assign the fields *)
  health = v 3; (* Give health a value of something, say 3 in this case. *)
}

let game_over () = print_endline "Game Over!"
let () = when_satisfied (player.health =? 0) game_over
#+end_src

そして次のように使えます。

#+begin_src ocaml
let () = player.health =: !(player.health - c 1) (* Nothing happens yet! player.health is 2 now. *)
let () = player.health =: !(player.health - c 1) (* Nothing happens yet! player health is 1 now. *)
let () = player.health =: !(player.health - c 1) (* Now something happens! player.health is 0 and "Game Over!" is printed to the screen! *)
#+end_src

*** なぜ作ったのか

もともと forcamla はゲーム向けに設計しましたが、汎用的な整理ツールとしても有用だと気づきました。Jane Street の [[https://github.com/janestreet/incremental][Incremental]] に似ていますが、forcamla は効率よりも使いやすさを優先しています。
      



* Typegist 0.0.0

Archive: https://discuss.ocaml.org/t/ann-typegist-0-0-0/18503/1

** Daniel Bünzli が発表しました


こんにちは。

~typegist~ の最初のリリースをお知らせできることを嬉しく思います。

#+begin_quote
Typegist は OCaml の型の本質を値として表現します。
この動的な型表現は、汎用的な型インデックス付き関数、すなわち値のシリアライザ、プリンタ、パーサ、差分ツール、乱数ジェネレータ、エディタ、FFI グルーなどを構築するために使用できます。アクセス可能な型であれば、そのパブリックインターフェースが定める限界まで記述できます。
Typegist は OCaml の型言語を完全にモデル化するのではなく、プロデューサーとプロセッサの両方にとって使いやすいインターフェースを提供するために、型インデックスメタデータで装飾されたコアな構造的サブセットに焦点を当てています。
Typegist は ISC ライセンスで配布されています。依存関係はありません。
#+end_quote

上述のとおり、これらの値は OCaml の型定義言語を部分的にしかモデル化していません。そのため、これらは ~Type.Repr.t~ 値ではなく ~Type.Gist.t~ 値となっています。typegist は型の忠実または正規の表現というよりも、型のためのデータインターフェース言語として捉えていただければと思います（実際にはその方が有用だと感じています）。

この表現は ~Stdlib~ の一部の型を特別扱いし、注釈を付けています。あまりに汎用的になり、他のシステムとのインターフェース時にすべてのセマンティクスが失われてしまうのは望ましくありません。例えば、JSON では ~list~ 値は配列として現れてほしいのであって、入れ子になった cons case オブジェクトとしてではありません。~None~ は ~null~ にマッピングされてほしく、定数 case オブジェクトではありません。テキストデータを保持する ~string~ 値は、16進数や base64 ではなく、プレーンな JSON 文字列として現れてほしいのです。

これは[[https://erratique.ch/software/typegist/doc/Typegist/Type/Gist/Expr/index.html][表現]]の一部が意図的にアドホックであることを意味します。OCaml の型式言語の無意味な詳細に煩わされることなく、自分自身の gist プロセッサを[[https://erratique.ch/software/typegist/doc/cookbook.html#generic_funs_template][合理的に簡単に]]構築できるよう、精度と汎用性のバランスを取っています。

次回 ~M.pp : t Fmt.t~ 関数を書く機会があれば、代わりに ~M.gist : t Type.Gist.t~ を書いてみてください。プリンタとそれ[[https://erratique.ch/software/typegist/doc/Typegist/Fun/Generic/index.html][以上のもの]]が手に入ります。また、~jsont~ のコンパニオンリリースとして、型の gist を ~jsont~ の JSON 型に[[https://erratique.ch/software/jsont/doc/Jsont_typegist/index.html][変換する]] 新しいオプションの ~jsont.typegist~ ライブラリも用意しました（JSON シリアライゼーションをお楽しみいただけます）。

typegist はあまり変更されないと思いますが、まだ実際の使用での試練を受けていません—でもすぐに始めるつもりです。これはリポジトリで長すぎる時間を過ごしてきた設計です。フィードバックに基づいて、より精度が必要な場合や、より良い表現が見つかった場合には、表現の変更が行われる可能性があります。ただし、そのような変更は主に gist プロセッサに影響するものになると予想されます。問題や改善点があれば、issue トラッカーでお知らせください。

型定義から gist を自動導出する手段を提案する予定はありませんが、過去に何人かがそれに興味を示してくれました。

楽しい型インデックスプログラミングを！

この最初のリリースは [[https://ocaml-sf.org/][OCaml Software Foundation]] からの助成金により実現できました。また、[[https://github.com/sponsors/dbuenzli][ドナー]]の皆さんにもサポートに感謝します。

- ホームページ: https://erratique.ch/software/typegist
- ドキュメント: https://erratique.ch/software/typegist/doc または ~odig doc typegist~  
- インストール: ~opam install typegist~（[opam PR]）

よろしくお願いします。

Daniel

* 依存型なしでの依存 if 式
:PROPERTIES:
:CUSTOM_ID: 4
:END:
Archive: https://discuss.ocaml.org/t/dependent-if-expressions-without-dependent-types/18506/1

** Didier Wenzek が発表しました


[[https://haskellforall.com/2026/09/dependent-if-expressions][Haskell for all のこの投稿]]では、Church エンコーディングを使って依存型なしで依存 if 式を実装する洞察に富んだ活用法が示されています。

以下の OCaml コードは型検査が通り、動作します。

#+begin_src ocaml
# let example bool = if_then_else bool 5 "hi!";;

# example t;;
 - : int = 5
# example f;;
- : string = "hi!"
# example (f && t);;
- : string = "hi!"
# example (f || t);;
- : int = 5
# example (not t);;
- : string = "hi!"
#+end_src

これは単純に Hindley-Milner 型推論に基づいており、Church エンコードされたブール型の型をあまり制限しないという単一のトリックを使っています。

ブール型を Church エンコードする最初のアイデアは、~then~ ケースと ~else~ ケースを同じ型に制限することでしょう
（forall 型をエンコードするためにレコードを使って）。

#+begin_src ocaml
type bool = { check : 'a. 'a -> 'a -> 'a; }
#+end_src

依存 if 式にはよりリベラルな定義が必要です。

#+begin_src ocaml
type bool = { check : 'a 'b 'c. 'a -> 'b -> 'c; }
#+end_src

そして、型を強制しない場合に推論されるのはこうなります
（forall 型の代わりに弱多相型が得られるという事実は無視して）。

#+begin_src ocaml
let t if_branch else_branch = if_branch
let f if_branch else_branch = else_branch

let if_then_else bool if_branch else_branch = bool if_branch else_branch

let (&&) a b if_branch else_branch = a (b if_branch else_branch) else_branch
let (||) a b if_branch else_branch = a if_branch (b if_branch else_branch)
let not a if_branch else_branch = a else_branch if_branch
#+end_src

ぜひ全文をお読みください。本当に素晴らしい読み物です。
      



* Caps 0.1.0、OCaml 向けケイパビリティ型システムおよびライブラリ
:PROPERTIES:
:CUSTOM_ID: 5
:END:
Archive: https://discuss.ocaml.org/t/ann-caps-0-1-0-a-capability-type-system-and-library-for-ocaml/18507/1

** Yoann Padioleau が発表しました


みなさん、こんにちは。

caps ライブラリの最初のリリースをお知らせできることを嬉しく思います。このライブラリを使用すると、OCaml プログラム（およびライブラリ）で「ケイパビリティ型」を使用できるようになります。

主なアイデアは、このライブラリを使用した後、関数が次のようなシグネチャを持てるということです。

#+begin_src ocaml
val foo: < Cap.network; Cap.stdout; Cap.random; .. > ->
  int -> float
#+end_src

これは、この関数が動作するために network、stdout、random の各ケイパビリティを必要とすることを意味します。シグネチャはこの関数が内部的に持つ副作用の種類と、内部的に行うシステムコール（またはその呼び出し先）を明らかにします。

このライブラリは Semgrep のコードベースで作業中に設計しました。コードベースの特定の部分を「サンドボックス化」または制御するのに有用で、若いエンジニアが特定の部分で危険な関数を呼び出せないようにするためです。新しいコーディングエージェント時代において、シグネチャで AI が生成するコードを制御するためにさらに有用だと思います。

詳細については、OCaml 2026 ワークショップでの発表をご覧ください: https://www.youtube.com/watch?v=4t_2wLz9EOo および対応するスライド https://aryx.github.io/ocaml-caps/caps.html（ここで何度か紹介された超クールな Slipshow プレゼンテーションツールを使用）。プロジェクトページ https://github.com/aryx/ocaml-caps もご参照ください。

opam 経由で簡単に試せます。

#+begin_example
$ opam update
$ opam install caps
#+end_example

質問があればお気軽にどうぞ。
      



* bstr、slice、bin（bigstring、バイナリフォーマット向けエンコーダとデコーダ）

Archive: https://discuss.ocaml.org/t/ann-bstr-slice-bin-bigstring-encoders-decoders-for-binary-formats/18509/1

** Calascibetta Romain が発表しました


[[https://github.com/robur-coop/bstr][~bstr.0.1.0~]] のリリース、および ~bin.0.1.0~ と ~slice.0.1.0~ のリリースをお知らせできることを嬉しく思います。これらのリリースは複数のライブラリを統合した作業の成果であり、[[https://robur.coop][私たちのコoperative]] 内でのフォーマットとプロトコルの実装に役立つものをまとめることを目指しています。特に、これらのライブラリは以下を提供します。
- _bigstring_ として知られるものを操作するための包括的なモジュール（[[https://github.com/inhabitedtype/bigstringaf][bigstringaf]] の代替 — あのライブラリの名前は長すぎるので）
- bigstring と bytes へのアクセスを提供するライブラリ（簡潔に言えば、[[https://github.com/mirage/ocaml-cstruct][ocaml-cstruct]] の[[https://github.com/robur-coop/bstr/blob/b427711671c1654df37550849efe5265c866ebcc/lib/slice.mli#L1][抽象化]]）
- 最後に、バイナリフォーマットを記述するためのライブラリ。エンコーダとデコーダを導出できます（[[https://github.com/mirage/repr][repr]] が提供するものの精神に倣って）

bigstring の利点を理解したい方のために、以前[[https://discuss.ocaml.org/t/buffered-io-bytes-vs-bigstring/8978/3?u=dinosaure][こちら]]で考えを共有しました。パフォーマンス上の理由（[[https://blog.robur.coop/articles/miragevpn-performance.html][この記事]]を参照）から ~ocaml-cstruct~ の使用を後退させましたが、bigstring は特定のケースでは依然として有用です: 根本的には、慎重に使用すべきです。

[[https://github.com/mirage/bechamel][~bechamel~]]（マイクロベンチマーク用）を使ったパフォーマンスには特に注意を払い、以下の結論が得られました。
- ~bstr~ は ~bigstringaf~ よりも優れたパフォーマンスを発揮します。~bigstringaf~ が開発された当時は存在しなかったタグを使用しているためです。
  |      | bstr   | bigstringaf |
  |------|--------|-------------|
  | blit | 4.4ns  | 4.8ns       |
  | sub  | 15.4ns | 18.9ns      |
- ~slice.bstr~ は ~ocaml-cstruct~ と同等のパフォーマンスを発揮します（予想通り）
- ~bin~ はデコードにおいて手書きコードに匹敵します
  |      | bin    | 手書き（~ocaml-cstruct~） | ~repr~ | ~angstrom~ |
  |------|--------|--------------------------------|-|-|
  | ipv4 | 11.9ns | 11.9ns                         | 93.9ns | 136ns |
  #+begin_src ocaml
let bin =
  let fn vihl tos total_length id ff ttl protocol checksum src dst =
    { version= vihl lsr 4; ihl= vihl land 0x0f; tos; total_length; id
    ; flags= ff lsr 13; frag_offset= ff land 0x1fff; ttl; protocol; checksum
    ; src; dst }
  in
  let open Bin in
  record ~name:"ipv4" fn
  |+ field ~name:"vihl" uint8 (fun t -> (t.version lsl 4) lor t.ihl)
  |+ field ~name:"tos" uint8 (fun t -> t.tos)
  |+ field ~name:"total_length" beuint16 (fun t -> t.total_length)
  |+ field ~name:"id" beuint16 (fun t -> t.id)
  |+ field ~name:"flags_frag" beuint16 (fun t ->
      (t.flags lsl 13) lor t.frag_offset)
  |+ field ~name:"ttl" uint8 (fun t -> t.ttl)
  |+ field ~name:"protocol" uint8 (fun t -> t.protocol)
  |+ field ~name:"checksum" beuint16 (fun t -> t.checksum)
  |+ field ~name:"src" beint32 (fun t -> t.src)
  |+ field ~name:"dst" beint32 (fun t -> t.dst)
  |> sealr

let cstruct cs =
  let vihl = Cstruct.get_uint8 cs 0 in
  let tos = Cstruct.get_uint8 cs 1 in
  let total_length = Cstruct.BE.get_uint16 cs 2 in
  let id = Cstruct.BE.get_uint16 cs 4 in
  let ff = Cstruct.BE.get_uint16 cs 6 in
  let ttl = Cstruct.get_uint8 cs 8 in
  let protocol = Cstruct.get_uint8 cs 9 in
  let checksum = Cstruct.BE.get_uint16 cs 10 in
  let src = Cstruct.BE.get_uint32 cs 12 in
  let dst = Cstruct.BE.get_uint32 cs 16 in
  { version= vihl lsr 4; ihl= vihl land 0x0f; tos; total_length; id
  ; flags= ff lsr 13; frag_offset= ff land 0x1fff; ttl; protocol; checksum
  ; src; dst }
  #+end_src

これらのライブラリは、bigarrays を扱うための一貫したライブラリセットを提供しつつ、パフォーマンスにおけるトレードオフをほとんど設けないという野心のもとに作られました。functor、GADT、ADT、さらには高階多相（ケイパビリティでさえも）を試すために[[https://github.com/dinosaure/buffet][いくつかの試み]]が行われました...

その結果、「貧者の functor」が十分であり、いくつかの調整（特に ~caml_apply2~ 呼び出しを避けるため）を加えることで、手書きコードと比較してかなり競争力のあるものが実現できました。

これらのライブラリは、bigstring を扱う際にコミュニティで欠けていたもの、または出現したものもカプセル化しています。私は完全に満足することなくこれらのライブラリの改善に個人的に貢献してきました: そのため特に ~bstr~ が生まれました。これらのライブラリのドキュメントとテストには相当の努力が注がれています。~bin~ に関する特定のアサーション（同型性など）を検証するためのファジャーも利用可能です。

これらのライブラリは現在使用中であり、このバージョンが最終版ではありません。特に OCaml でのプロトコルとフォーマットの実装に関連して、引き続き改善を続けていく予定です。

私たちの仕事を評価いただける方は、[[https://github.com/sponsors/robur-coop][GitHub 経由]]または[[https://robur.coop/#donate][私たちのチャリティ]]に直接寄付をお願いします。楽しいハッキングを！

Giovanni Girolamo Saccheri の誕生日を祝して、OCaml バージョン 5.5.1 のリリースをお知らせできることを嬉しく思います。

このリリースでは、macOS 上でコンパイラをクローンするサポートも復元されています。

すでに OCaml 5.5.0 を使用している場合は、OCaml 5.5.1 への移行を強くお勧めします。

*** Slipshow 0.13.0: Juraslip Park

数十年前のソフトウェアを掘り起こしていたところ、今は絶滅した Keynoplodocus、Googloslideraptor、そして最後に Powerpointaurus Rex の DNA を含むバグを発見しました。

それを Slipshow 自身の DNA にマージすることで、現代のあらゆるソフトウェア（Slipshow も含む）が忘れていた機能、つまりマウスを使ってプレゼンテーション内の要素を配置する機能を復活させることができました。

#+attr_html: :width 80%
https://github.com/user-attachments/assets/2330aab5-ee28-4248-b215-66920cb1c7ff

このリリースの主な新機能は「GUI モード」です。

これまで Slipshow は、CSS をエスケープハッチとして使いながら、要素の種類（タイトル、段落、ブロック）に基づいてすべての要素を自動配置していました。これが「What You See Is What You Mean」モデルです。「What You See Is What You Get」では対照的に、レンダリングされたコンテンツを直接編集し、通常マウスで要素を配置します。

両方の（ジュラシック）世界の最良の部分は「What You See Is What You Want」: 要素ごとにどちらのモードを使うか選択できます。

一部のカエルが単性別環境で性別を変えられるように、Slipshow の要素も ~gui~ 属性1つで WYSIWYM から WYSIWYG に変わり、マウスで配置できるようになりました:

#+begin_example
    {gui}
    Drag me, resize me.
#+end_example

その他の主な改善点として、レンダリングされたコンテンツを Ctrl+クリックしてソースに移動する機能、[[https://tachyons.io/][Tachyons]] CSS フレームワークの追加、より一貫したショートカット、描画エディタのユーザビリティ改善などがあります。

いつものように、すべての[[https://github.com/panglesd/slipshow/graphs/contributors?from=5%2F30%2F2026][コントリビューター]] 💚、[[https://github.com/sponsors/panglesd/][スポンサー]] ❤️、そしてこの作業を可能にしてくれた[[https://nlnet.nl/project/Slipshow/][NLnet の寛大な助成金]] 💝 に感謝します！

* TyXML 5.0.0
:PROPERTIES:
:CUSTOM_ID: 11
:END:
Archive: https://discuss.ocaml.org/t/ann-tyxml-5-0-0/18516/1

** Vincent Balat が発表しました


**TyXML 5.0.0** のメジャーリリースをお知らせできることを嬉しく思います。TyXML は HTML および SVG ドキュメントを構築するライブラリで、その正当性が OCaml 型システムによって検証されます: 仕様が特定の位置で許可していない要素は型検査を通過しません。このライブラリは現在の仕様、HTML については WHATWG living standard、SVG については Filter Effects モジュールを含む SVG 2 に準拠するようになりました（SVG サポートは SVG 1.1 以来更新されていませんでした）。

主なハイライト:

- **HTML**: popover、invoker commands、microdata、declarative shadow DOM と CSS shadow parts、~loading~/~decoding~/~fetchpriority~、~blocking~、新要素 ~s~、~bdi~、~search~、~data~、~slot~、~track~、不足していたイベントハンドラ属性（pointer ファミリー、クリップボード、~ontoggle~、~onscrollend~ など）、標準に合わせたコンテントモデル。
- **SVG**: ~mask~ は ~Svg_types~ で宣言されていたが要素自体がなかった、~feMerge~ に ~feMergeNode~ が存在しなかったため子要素を持てなかった、約30個のプレゼンテーション属性に型タグはあったが生成する関数がなかった、これらすべてが追加され、SVG 2 の追加、ARIA サポート、SVG 2 のリンク属性、SVG 2 に拡張されたコンテントモデルも含まれています。
- **PPX と JSX 構文**: camelCase の SVG 属性が認識されなかったため、~viewBox~、~stdDeviation~、~preserveAspectRatio~ などほとんどのものが拒否され、PPX では実際の SVG をほとんど書けなかった。コンテントモデルがテキストを受け付けない場所では SVG タグ間の空白が無視されるようになり、インデントされた SVG が型検査を通るようになりました。
- **実際には使用できなかった構造体の修正**: ~area~ に ~href~ がなく、コンテントモデルにそのタグがなかったため、area を含む ~map~ はどこにも収まらなかった；~symbol~ がコア属性（つまり ~id~ もなく参照もできなかった）を受け付けなかった；~menu~ の ~li~ 子要素が構築できなかった。いくつかの属性名もスペルミスで出力されており、これはコンパイルエラーよりも悪かった（出力が正常に見えるため）。知っておくべき破壊的変更: ~hidden~ と ~contenteditable~ は列挙引数を取るようになった、URL 値の属性は ~Xml.uri~ を通る、SVG ドキュメントは SVG 1.1 doctype なしで印刷される、ファンクタインターフェースの実装者向けに ~Wrapped_functions~ に4つの新しい関数が追加された、ビルドには OCaml 4.08、dune 3.18、ppxlib 0.36 が必要。

opam install tyxml
#+end_example
