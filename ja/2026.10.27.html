uniker.nl - OCaml によるユニカーネル

Archive: https://discuss.ocaml.org/t/ann-uniker-nl-unikernels-in-ocaml/18625/1

Calascibetta Romain が発表しました

新しいウェブサイト uniker.nl の公開をお知らせできることを嬉しく思います。このウェブサイトは、OCaml 5 を用いたユニカーネル開発への新しいアプローチを体現しています。ユニカーネルの開発に新しい方法を提供するとともに、ユニカーネルのデプロイと利用にも同等の重点を置いています。このサイトには包括的なチュートリアルとリソースが掲載されており、OCaml におけるユニカーネルに興味を持つ方への_最初の入口_として、新しいエコシステムを理解するための手助けをします。

このサイトのコンテンツはこちらで公開されており、優れた YOCaml プロジェクトによって動作し、私たちの immuable ユニカーネルを用いてデプロイされています。

新しいエコシステム

OCaml Workshop 2026（スライド）にて新しいワークフローを発表しました。私たちのアプローチは主に2点に要約できます：

  • ユニカーネルの開発
  • ユニカーネルのデプロイとその利用
  • ユニカーネルを開発するために

    私たちの協同組合はかなり長い間ユニカーネルの開発を続けてきました。私たちのブログでは、インフラに使用しているいくつかのユニカーネルを紹介しています。経験を通じて、ユニカーネルという形でアプリケーションを開発する際の制約や限界を十分に認識しています。最もよく知られた制約として、プロトコルやフォーマットに関してPOSIXインターフェースを必要としない（またはそれを模倣しようとしない）ことを受け入れています。今日でも守り続けているルールの一つは、実装を提供する際にI/O やスケジューラに依存しない1ことです。

    この経験から、ユニカーネル以外のコンテキストでも他の人々が使用しているプロトコルやフォーマットを開発することができました。

    一方で、特に MirageOS が現在提供しているものに関して、達成できることの限界も見えてきました。これを念頭に置き、ユニカーネル開発における制約（特にクロスコンパイルに関して）をさらに検討した結果、2つのツールを用いてユニカーネルの開発を構造化することにしました：[~unic~](依存関係を推論して_vendor_する方法)と[~mfetch~](依存関係を vendor する方法)です。

  • unic: 依存関係を推論して_vendor_する方法

    ユニカーネルにおける制約の一つは、Cファイルをホストシステムに既存のものに依存しないよう特定のオプションで再コンパイルする必要があることです。MirageOS 3 が取ったアプローチは、このような特定のコンパイル結果をCスタブを含むライブラリ（digestifやmirage-cryptoなど）の中に配布することでした。問題は、ユニカーネルの中核コンポーネントである Solo5 向けのCファイル固有のコンパイル環境を得るために、これらのライブラリのユーザーに ocaml-solo5 のインストールを強いていたことです。

    MirageOS 4 では dune とそのコンテキストが導入され、Cファイルに対して一貫したコンパイル環境を実現できるようになりました。しかしこのアプローチは新たな制約をもたらしました：ユニカーネルのすべての依存関係が dune を使用しなければならなくなったのですが、OCaml エコシステムではそうでないケースも正当に存在します。

    そこで私たちは、一部のライブラリを再コンパイルする必要性をさらに精査し、最終的に ocaml-solo5 の重要な利点を活かすことにしました。それは、このコンパイラでOCamlファイルをコンパイルしても、ホストのOCamlコンパイラを使った場合とまったく同じ結果が得られるという点です。つまり、最初からそうであったように、厳密にCファイルのみをクロスコンパイルすればよいのです。

    この2つの特性（Cファイルのみをクロスコンパイルすればよいこと、ホストコンパイラでコンパイルした純粋なOCamlで書かれたライブラリを再利用できること）の交点において、dune を使用していないライブラリのメンテナンス作業を一切行わずに、また必ずしもすべてを再コンパイルしなくても、次のようなコードを書く機能をユーザーに提供できます： 

    $ opam install unic
$ cat >main.ml<<EOF
> open Digestif

> let () = Mkernel.run [] @@ fun () ->
>   Fmt.pr "%a\n%!" SHA1.pp (SHA1.digest_string "Hello World!")
> EOF
$ unic infer -r .
Module Digestif is provided by several ocamlfind packages:
  [0] digestif.c
  [1] digestif.ocaml
Pick one [0-1]: 0
digestif
mkernel
$ opam source digestif
$ opam source mkernel
$ dune build
$ solo5-hvt -- _build/solo5/main.exe --solo5:quiet
2ef7bde608ce5404e97d5f042f95f89f1c232871Solo5

    unic は、特定のビルドシステムを使わずにOCamlプロジェクトの依存関係を推論し、ユニカーネルを生成するためにクロスコンパイルが必要なもの（この場合 digestif と mkernel ですが fmt は不要）を計算できるツールです。このプロジェクトはまず私たちの目的のために作られていますが、静的リンクされた実行ファイルをコンパイルする際にも有用である点は注目に値します。

    このツールはMETAファイルの解析、成果物を様々な観点（モジュール名、ocamlfind パッケージ名、OPAMパッケージ名）から閲覧、OCaml成果物（*.cmxa ファイルなど）の解析など、多岐にわたるサブツールを提供しています。

    特に @Octachron の codept プロジェクト（unic はこれをベースにしています）と、それを改善するために協力していただいたことに深く感謝します。

  • mfetch: 依存関係を vendor する方法

    クロスコンパイルが必要な依存関係をより正確に特定できたので、次はそれらをダウンロードする必要があります。opam source は十分に機能しますが、以下のような様々なソースタイプからソースコードをダウンロードできるツールが欲しいと考えました：

    • 通常の場合と同様に tarball から
    • Gitリポジトリから
    • またはファイルシステム上の特定の場所から

    そこで mfetch を開発しました。OPAMまたはユーザーが提供する情報を元にソフトウェアのソースをダウンロードし、すべてのソースを含む vendors フォルダを作成することができます。 

    $ unic infer -r . -o _mfetch
$ mfetch --with-dune-file
 digestif                 │██████████████████│    3.1 MiB /    3.1 MiB    5.9 MiB/s 
 mkernel                  │██████████████████│   37.3 KiB /   37.3 KiB    3.4 MiB/s 

digestif                         ok
mkernel                          ok
$ dune build

    mfetch では、ソースファイルを変更したかどうかの確認（バグ修正のため）や、*.locked ファイルの生成も可能で、別のツール orb を使ってユニカーネルの再現性を検証することができます。このツール自体は革新的なものではありませんが、ワークフローを合理化するのに役立ちます。 

    $ mfetch status
digestif                         ok
mkernel                          ok
$ mfetch lock
2 sources locked into _mfetch.locked
  • OCaml 5 向けライブラリ

    新しいワークフローでは OCaml 5 を使用します。OCaml 5 でユニカーネルを生成するために必要な基本的な構成要素を更新するとともに、主にエフェクトを活用できるライブラリ群も開発しました。さらに、過去数年間で以下を開発しました：

    • Miou：OCaml 5 向けスケジューラ
    • mkernel：Solo5 が提供するI/Oを扱うために設計した Miou スケジューラの派生版
    • mnet：エフェクトを用いたOCamlによるTCP/IPスタックの再実装（utcp を使用）
    • mhttp、msendmail、mfat、vifu などのその他多数のライブラリ

    現在デプロイ済みのいくつかのユニカーネルで使用されているこれらのライブラリにより、開発者に対してユニカーネルを実装するための_ダイレクトスタイル_アプローチを提供できます。

    しかしこの新興エコシステムで重要なのは、過去のプロジェクトに対する回顧的な分析を行い、同じ過ちを繰り返さないようにすることです。lwt（MirageOS スケジューラ）を使用した既存のライブラリを Miou（またはエフェクトを使用する他のスケジューラ）に移行することが非常に難しいことに私たちはすぐに気づきました。そこで、Miou を使ったダイレクトスタイルアプローチを提案するだけでなく、MirageOS でユニカーネルをデプロイして得た教訓を踏まえてライブラリの実装を見直す機会としました。メモリ使用量、過去の実装での既知のCVEの回避（私たちはOCamlセキュリティチームの一員でもあります）、そしてfunctorに系統的に依存しない代替APIの提供に特に注意を払いました。

    このアプローチはまだ実験的です。複数のレイヤーにわたってこの新しいエコシステムを統合する必要がありますが、デプロイ済みのユニカーネルで観察したことに基づき、これらの新しい実装が過去のものよりも大幅に優れているという確信があります。

  • ユニカーネルをデプロイするために

    ユニカーネルのもう一つの側面はデプロイです。ユニカーネルを開発する（そして開発を容易にする）だけでなく、デプロイして使用することも重要です。私たちの主な目標は既存のサービスをユニカーネルに置き換えること（ネームサーバー、ウェブサイト、タイムサーバーなど）であり、既存のインフラと競合する方法は積極的にユニカーネルをデプロイして使用することです。

    そのため、以下の2つのプロジェクトを開発しました：

    • Albatross：ユニカーネルを起動するOCamlサービス
    • Aussi：Solo5 向けOCIランタイム

    Albatross は主に、ユニカーネルの再現性を検証するインフラ builds.robur.coop と組み合わせて使用しています。これにより、ユニカーネルの依存関係（特にCVE）を追跡し、サプライチェーンのセキュリティを確保できます。

    次はデプロイです。ユニカーネルを既存のインフラに統合し、特に InfluxDB、Telegraf、Grafana を使ったモニタリング手段を提供することを目指しています。

    このようにして、以下のようなサービスを提供できています（一部はまだ mkernel~/~mnet に移植されていませんが、まもなく行われます）：

    • unipi や immuable を使った https://blog.robur.coop/ などのシンプルなウェブサイト
    • プライマリ DNSサーバーとセカンダリサーバーを通じた robur.coop、reyn.ir、din.osau.re などのドメインのDNS管理
    • MirageVPN または Zostera を使ったVPNサービス
    • タイムサーバー（Chaos を使用）：https://chaos.osau.re/
    • CalDAV カレンダーシステム
    • ptt プロジェクトを使ったメーリングリスト
    • tlstunnel や contruno などのTLS終端プロキシ（sherlocode.com で使用）
    • その他多数！

    実際の使用を通じてユニカーネルとそれに依存するライブラリを改善しています。そのため、チュートリアルの一部ではユニカーネルのデプロイにも焦点を当てており、使用してフィードバックで協力していただけるようにしています。

    最後に、Mollymawk というプロジェクトも提案しています。これはウェブインターフェースを通じたユニカーネルのデプロイを簡素化するために設計されており、将来的には使用を希望する誰もが私たちのインフラへのアクセスを提供できるようにしたいと考えています（様々な試みをしてくれた @kit-ty-kate に感謝します）。

ユニカーネルと MirageOS

熱心な方々は、私たちのアプローチが私たちのメンテナンス作業によって現役を保つ MirageOS と比べてどのような利点があるのか疑問に思うかもしれません。私たちのアプローチは、ユニカーネルの普及を妨げるガラスの天井として特定した5つの点によって特徴づけられています：

  • 最初の点は ocaml-cstruct の使用に関するものです。根本的な問題は、_バッファ_として bytes~/~string の代わりに bigarray を使用していることです。MirageVPN の開発経験から、エコシステム全体で バッファ の概念として cstruct を系統的に使用することが、ユニカーネルのスループットにおける最大のペナルティであることがわかりました。そこで、bstrとsliceを開発するだけでなく、cstruct を bytes~/~string に置き換えてほとんどのライブラリを書き直すことにしました（ocaml-tls、mirage-crypto、ocaml-dns、最近では awa-ssh と utcp がその例です）。結論は単純です：bigarray の使用をやめるのではなく、APIでその使用を系統的にしないことです。
  • 2点目は、ユニカーネルが必要とするデバイスを表現するためのfunctorの使用に関するものです。これらのデバイスを具体化する特定の実装をfunctorを通じてインターフェースを再利用して注入するアプローチは魅力的に見えますが、最新の概念に対応していないインターフェースによって制約されたエコシステムのメンテナンスコストが、より特定のユニカーネルを開発する必要があるたびに不合理な状況を招きました。再び言いますが、functorの使用をやめるのではなく、系統的にしないことがルールです。

  • 3点目はユニカーネルのコンパイルに関するものです。MirageOS は今日でも dune とうまく統合されていない回避策に依存しています。これは「マルチステージコンパイル」として定義でき、望むターゲットに応じてコード生成フェーズが必要になります。このようにツールによって指定される依存関係のセットでワークフローを構造化する方法は、開発者が何を、どのようにしたいかを明示的に制限します。ユニカーネルのコンパイルには制約（Unix モジュールを使用しないことなど）がありますが、私たちの協同組合は、ユニカーネルの設計においてユーザーを支援する（しかし強制しない）情報提供的（規範的でない）ツールを提供することにしました（さらに、unicとmfetchを紹介できることも嬉しく思います）。新しいアプローチのポイントは、ユニカーネルの開発においてツール（mirage）ではなくユーザーが最終決定権を持つことを確保することです。

    mirage ツールが行うことは非常に複雑で、functor適用の生成や初期化スタブ、opamバージョン制約（functorや初期化関数が新しいopamパッケージで変更される可能性があるため）などが含まれます。mirage ツールはクローズドワールド仮定を持ち、mirage が認識していないパッケージの使用は非常に困難であり、mirage ユニカーネルで js_of_ocaml を使用することも非常に難しいです。

  • 4点目はこのエコシステムのメンテナンス、特に MirageOS が依存するツールとライブラリのメンテナンスに関するものです。さらに、opam-monorepo に失望する経験をし、OCaml 5 に合わせて mirage-tcpip を更新することが日々ますます困難になっていることがわかります。OCaml セキュリティチームへの関与から、メンテナンスの欠如により特定のライブラリを廃止したいという気持ちにもなっています。そこで、エコシステムを私たちの協同組合が生産・メンテナンスするものに再集中させています。
  • 最後に、AIの台頭にもかかわらず変わらないコミュニティとの活動があります。ユニカーネルに関する存在しない問題を解決するためにAIが乱用されており、それがセキュリティ、メンテナンス、ソフトウェアの品質に関する私たちの信頼性を損なっていると考えています。この点において、デプロイよりも バイブコーディング を好む人々から距離を置こうとしています。このアプローチはライセンスとして AGPL を使用すること（デュアルライセンスの選択肢も提供しつつ）と、AIの使用に関する POLICY に反映されています。

これらすべてが、MirageOS 4（私がリリースマネージャーを務めた）の失敗を特徴づけた要因から根本的に離れる MirageOS 5 を提案するに至りました。この敗北を認め（そして分析した上で）、ユニカーネルの作成とデプロイへの新しいアプローチを提案します：uniker.nl。

MirageOS プロジェクトに関連するプロジェクトについては、もちろんいくつかは引き続きメンテナンスしつつ、私たちのいくつかのライブラリを使用している方々に、より最新のソリューションを提供していきます。また、新しいライブラリとツールへの移行を希望する方を喜んでお手伝いします。私たちは常にそうであったように、サポートのために利用可能です。

segmap の発表：リネーミングのための高速データ構造

こんにちは！segmap を発表できることを嬉しく思います。この OCaml ライブラリは segment maps を実装しています。これは自然数から自然数への単調増加関数を表す純粋関数型データ構造です。このデータ構造は、ルックアップ、逆ルックアップ、水平および垂直の変位、先頭への挿入、合成、meet、join など多くの操作を効率的にサポートします。このデータ構造は、変数が de Bruijn インデックスまたは co-de Bruijn インデックスとしてエンコードされる証明支援系、コンパイラ、シンボリック計算システムに役立つ可能性があります。

このデータ構造はこちらの論文で説明されており、ライブラリのドキュメントもオンラインで公開されています。 

opam update
opam install segmap

Happy hacking, FP.

hexen.0.1

Archive: https://discuss.ocaml.org/t/ann-hexen-0-1/18627/1

Mikhail が発表しました

やあ！

16進数の部分文字列をデコードする必要があったので、Hexen を書きました。これは16進数バイトシーケンスのエンコードとデコードを行うまた別のライブラリです。

このライブラリの主な目標は、任意の出力先（bytes またはバッファ）への部分文字列のエンコードとデコードのための柔軟なAPIを提供することです。

使い方

Hexen は、文字列や部分文字列のエンコードとデコードのための高レベル関数 encode と decode を提供します。 

Hexen.encode "Hello World";;
(* - : string = "48656c6c6f20576f726c64" *)

Hexen.decode "48656c6c6f20576f726c64";;
(* - : string = "Hello World" *)

Hexen.encode_substring "Hello World" 0 5;;
(* - : string = "48656c6c6f" *)

Hexen.decode_substring "48656c6c6f20576f726c64" 0 10;;
(* - : string = "Hello" *)

また、Hexen は文字列や部分文字列を既存のバッファや bytes に直接エンコード・デコードする関数も提供しています。 

let buffer = Buffer.create 16 in

Hexen.encode_to_buffer "Hello" buffer;

stele 0.1.0: Menhir 文法の構文エラーメッセージ生成ツール

Archive: https://discuss.ocaml.org/t/ann-stele-0-1-0-syntax-error-messages-for-menhir-grammars/18657/1

Jérôme Vouillon が発表しました

Menhir 文法の構文エラーメッセージを自動生成するツール stele の最初のリリースをお知らせできることを嬉しく思います。

不正な入力に出会った Menhir パーサーは Error を発生させますが、これはパースが失敗した場所は示しますが、理由は示しません。Menhir はすべてのエラー状態（パースが詰まる可能性のある全ての時点）に対してメッセージを記述すれば、実際のメッセージを表示できますが、現実的な文法にはそれが数百もあり、文法が変わるたびに古くなります。

stele は、menhir --list-errors と文法の .cmly から、ビルド時にメッセージを生成します。いくつかのエイリアスと1つの %on_error_reduce アノテーションがあれば、チュートリアルの計算機は次のように報告します： 

Error: Assuming that the statements are complete, expecting '}'.
 --> stray.calc:1:6
1 | { 1; ) }
  ·      ^
  ·   ^^ these statements
  · ^ This '{' opens the enclosing construct.

得られるもの：

  • すべてのエラー状態に対するメッセージ：次に何が来られるかを示します。各リストはパーサーのテーブルと照合されるため、そのメッセージがパーサーがその状態で拒否するトークンを提示することはありません。
  • 位置のヒント：入力がまだその中にある開きデリミタと、パーサーが完結したと仮定した構文要素。小さなランタイムライブラリ stele.runtime は、パーサーが失敗したときにこれらをソーススパンに変換します。menhirLib にのみ依存しているため、js_of_ocaml と wasm_of_ocaml でも動作します。レンダリングはユーザーに任されており、Grace と組み合わせるとうまく機能します。
  • 必要なときのより良い表現：小さな設定ファイルで読みやすい名前とトークングループ（「演算子」など）を指定でき、オーバーライドファイルには手書きのメッセージが必要な少数の状態のものを保持できます。どちらにも古いエントリがあるとビルドが失敗します。

stele は François Pottier のReachability and Error Diagnosis in LR(1) Parsers（CC 2016）——--list-errors の背景にある論文——に基づいています。この論文が CompCert のパーサーに対して手作業で行ったことを自動化します。Wax ツールチェーンの内部で始まり、そこでは2つの文法のエラーメッセージを生成しています。

試すには： 

opam install stele

OCaml ≥ 4.14 と menhir ≥ 20260122 が必要です。チュートリアルでは、小さな計算機の文法を「構文エラー」からフルセットアップまで10段階で説明しています。その最終状態はコピーして実行できるサンプルです。

Str partial-match によるキャプチャレジスタの古い値によるアンダーフロー

ANT-2026-KKC4QS4S Str partial-match stale capture registers underflow

Str.string_partial_match はキャプチャされたグループの開始と終了を記録します。 beginning <= end という暗黙の前提がありました。 しかし、マッチされた文字列の終端に達したが正規表現の終端には達していない場合、 グループの開始がスター演算子のN回目の繰り返しでマッチし、 グループの終了がN-1回目の繰り返しでマッチすることが可能で、 beginning > end になる可能性がありました。 Str.matched_group は安全で、beginning > end のグループに対して Invalid_argument で失敗しますが、Str.replace_matched はクラッシュする可能性があり、 end - beginning バイトを memcpy しようとします。

ANT の例は、\(\(a\)b\)+ に対して ab を部分マッチさせるケースです。 グループ2は beginning = 2、end = 1 となります。

修正

修正は beginning > end のグループをマッチしなかったものとして記録することです。

影響を受けるか？

以下の条件をすべて満たす必要があります：

  • Str.string_partial_match を使用している必要があります
    • この関数を使用していない場合は影響を受けません
  • Str.string_partial_match の呼び出し後に同じ正規表現で Str.{replace_matched,global_replace,replace_first} のいずれかを使用する必要があります
    • Str.group_beginning と Str.group_end を使用して独自の文字列操作を行う場合は安全です（String モジュールが境界外アクセスで例外を発生させるため）。同様に Str.matched_group も安全です（OCaml 実装で String 関数を使用しています）
  • マッチの置換が0より大きいグループを参照する必要があります
    • 置換文字列引数が固定されていてグループを参照しないか、グループ0のみを参照する場合は影響を受けません
  • 参照される置換グループが元の正規表現の繰り返し演算子の下にある必要があります
    • 正規表現に繰り返し演算子がない場合、または繰り返し演算子の下にグループがない場合は影響を受けません

例えば、{|\(\(a\)b\)+|} を Str.string_partial_match の呼び出しの正規表現として使用し、 その後 Str.replace_matched の引数で \2 を参照している場合に影響を受ける可能性があります。
